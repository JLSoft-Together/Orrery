## 2. Thiết kế
- Crate `apps/core/crates/core-transcript` + subcommand `orrery-core transcript` (stdin / stdout NDJSON như `procs`, collector tự spawn 1 con, thoát khi stdin EOF). Không bind port.
- Ranh giới đích (b): Rust đọc file → dựng `TerminalSession` / `Agent[]` / `ToolSpan[]` / `ActivityDraft[]` / usage bucket delta; Node chỉ còn store + diff + WS server. Đi qua bước đệm (a) `Signal[]` để parity từng tầng.
- Usage index sang Rust trước (độc lập, lợi CPU lớn nhất ở cold scan): đọc / ghi đúng `usage-index.json` v4 (cả hai chiều trong giai đoạn song song), dedupe `message.id` toàn cục, `gone` / `releaseIds`, `renameWithRetry`.
- Cờ `CCM_CORE_TRANSCRIPT=rust|node` (mặc định `node` tới khi qua cổng), `CCM_CORE_USAGE=rust|node` riêng cho usage. Core lỗi → đường Node cũ.
- Redaction giữ y: whitelist field, `MAX_ENUM` 120, regex `EFFORT_RE` / `AGENT_ID_RE` / `RECORD_ID_RE`, `reply_text` ≤ 3000 ký tự, `maskSecrets`, `sockKey` sha256. Rust không log nội dung dòng JSONL.
- Watch: crate `notify` (ghi lý do) hoặc giữ `fs.watch` ở Node rồi đẩy tên file sang Rust (giai đoạn đầu: Node đẩy, Rust không tự watch).

### 2.1 Protocol `orrery-core transcript` (T1, usage)
- NDJSON stdin / stdout, 1 MiB max request line. Request = object with `op`, number / string `id` (no id → no reply; only `usage.notify` is sent without id). Reply `{id, ok:true, …}` or `{id, ok:false, error}`; events carry `event` and no `id`.
- `ping` → `{version}`.
- `usage.scan {projectsDir, cacheFile|null, sweepMs?, fileDebounceMs?, saveDebounceMs?, idRetentionMs?}` (= `UsageIndex.start`): loads cache v4, replies `{snapshot}` (= first `resetUsage`), then queues the full scan and starts the sweep timer. Second open → `open`; bad args → `projectsDir` / `cacheFile`.
- `usage.notify {files: [rel with /]}` (= `notify`; debounce per file in Rust; max 4096 names per line). Node normalises `path.sep`.
- `usage.query {q}`: `heatmap {days, today?}` → `{heatmap}`, `toolStats {days, project|null, today?}` → `{toolStats}`, `scanInfo` → `{scan}`, `snapshot` → `{snapshot}`. `days` integer 0..3660 (else `days`), `today` default = local today. Answered on the main thread between files of a running scan.
- `usage.idle` (= `whenIdle`) answers when the job queue reaches it. `usage.stop` (= `stop`) stops the scan at the next file, saves if needed, answers. Before open: `closed`. Unknown op → `op`.
- Events: `usage.scan {scan}` (= `setUsageScan`, start + every > 400 ms), `usage.reset {snapshot}` (scan done), `usage.update {buckets}` (dirty buckets after notify / sweep).
- stdin EOF → stop + save + exit 0. stderr: `[collector] usage index: <io error>` / `cannot save usage cache: …`, never line content.
- Known differences vs Node (edge cases only): lone UTF-16 surrogate when a name is cut at 100 units (Rust drops the half), JSON nested deeper than 128 or numbers beyond f64 range (serde_json rejects the line, JS counts it), `Date.parse` non-ISO forms, `localeCompare` ties outside ASCII (approximation), local time from the OS zone instead of ICU.

### 2.2 Protocol `orrery-core transcript` (T2, signals)
- Same process / NDJSON as §2.1; `signals.*` handled on the main thread before the usage ops; one read is capped by `maxBytes` (default 4 MiB), so usage / ping replies wait at most one page. No events.
- `signals.open {file, lite?: bool, toolUseIds?: string[], spans?: {terminalId, agentId}, chunkBytes?, fromEnd?, maxLine?}` → `{handle}` (number). `lite: true` = tracker `liteFilter` with `toolUseIds` as `agentToolUses` (else `signalLineFilter`); `spans` adds a per-handle `ToolSpanLog`. `maxLine` default 64 MiB (longer lines dropped whole, as `JsonlTailer` `maxLine`; TS tracker has no max). Errors `file` (missing / empty), `lite` (not bool), `toolUseIds` (not array or > 20 000 ids), `spans` (no `terminalId` / `agentId`), `handles` (4096 open).
- `signals.read {handle, toolUseIds?, nowMs?, maxBytes?}` → `{signals: Signal[], state, spans?: ToolSpan[], offset, more?: true}`: reads from the current offset towards the size at stat time like `JsonlTailer.readEach` (partial line kept, truncate → from 0), but at most `maxBytes` (default 4 MiB) per call; `more: true` = call again, the next calls keep the same target size (and the size the lite filter sees) until it is reached, so the pages add up to one TS `readEach`. `signals` / `spans` are this page only, `state` is after this page. `signals` = `extractSignals` of every new line in order (shape of `transcript.ts` `Signal`, camelCase, absent fields omitted). `state` = `TranscriptState` after the read: `openTools` ([id, name] in Map order), `codexCalls`, `deviceCallAt?`, `portConflict? {port, at}`, `model?`, `effort?`, `cacheTtl?`, `cacheAt?`, `lastAt?`, `contextTokens?`, `firstContext?`, `peakContext`, `compactions`, `permissionMode?`, `gitBranch?`, `ended`, `lastEndAt?`, `limitHit? {at, resetsAt?, window?, autoResume?}`, `lastReply?`, `tokens? {input, output, cacheRead}`, `currentTool?`, `pendingAsk?`. `spans` = spans changed by this read (`ToolSpanLog.apply`, prune with `nowMs`, default now). `toolUseIds` replaces the lite set before reading. Error `handle`.
- `signals.close {handle}` → `{}`; error `handle`. A `signals.*` line without `id` is ignored (nothing runs); unknown `signals.*` → `op`.
- JSON like `JSON.parse`: nesting deeper than 128 → parsed without depth limit on a thread whose stack grows with the `[` / `{` count (16 MiB + 2 KiB per level, max 1 GiB, beyond that the line is dropped), the value is dropped on that thread; numbers out of f64 range (`1e400`, `-1E999`, `-2e308`) are read as `-1`, which every signal path treats like JS `±Infinity` (`int()` → 0, `typeof` number kept, `resetsAt > 0 && finite` fails).
- Never on stderr: line content. Known differences: plan §2.1 list (except depth / number range, handled above); `js_slice` at 120 (branch / mode / trigger), 3000 (reply), 200 (ask question), 60 (ask label), 80 (span tool) never cuts a surrogate pair, so where JS keeps a lone high surrogate Rust drops it; lone `\ud800` escapes in a line → U+FFFD; `limit_hit.resetsAt` beyond the Date range (±8.64e15 ms) → Rust omits the field where TS throws `RangeError`.

### 2.3 Protocol `orrery-core transcript` (T3, tracker)
- Same process / NDJSON; `tracker.*` handled on the main thread before `signals.*` and the usage ops. One `tracker.sync` page reads at most `maxBytes` (default 4 MiB) across main + subagent files, so `ping` / `usage.query` wait at most one page (decision: paging on the main thread, no worker thread; replies stay in request order).
- Ops = the `SessionTracker` methods that touch files; everything synchronous stays in TS (`coreTracker.ts`): `buildTerminal` / `buildAgents` / `codexCalls` / `lastDeviceCallAt` / `lastPortConflict` / `lastReply` / `pendingAsk` read the last `view`, `toolSpans` / `closeOpenSpans` read a span mirror (`spanMirror.ts`), `setRecord` / `markEnded` / `shell` / `parentPid` / hints stay in TS. Reason: `monitor.ts` calls these synchronously between syncs (status line, alias, record change) with record / hints Rust never sees, so Rust returns the state and TS builds `TerminalSession` / `Agent[]` with the same code as `tracker.ts` (deviation from boundary (b): Rust stops at the per-agent state, not the shared shapes).
- `tracker.open {key, terminalId, projectsDir}` → `{}`. `key` = TS-chosen unique string (never reused, so a stale key after a core restart cannot hit another tracker). Errors `key` (missing / already open), `terminalId`, `projectsDir`, `trackers` (4096 open).
- `tracker.sync {key, sessionId|null, cwd|null, epoch, catchUp, plan: {all?, unresolved?, files?: basenames (max 4096)}, nowMs?, maxBytes?}` = one `syncOnce`: `epoch` differs from the last one → reset session state (TS bumps it on `sessionChanged`), find transcript (`findTranscript`: cwd slug, then every project dir), read main (if planned or first found), discover `agent-<id>.meta.json`, read wanted subagents (lite catch-up = `isLiteCatchUp` with `nowMs`), resolve, prune spans. Reply `{activity, spans, inbound, sent, view?, more?}`:
  - `activity` = `ActivityDraft[]` in TS order; `tool.started` may carry `touch` (= `ToolTouch`), the seam strips it and appends the `sensitive` drafts from `hints.sensitive.check` right after (sensitive rules / project roots stay in TS).
  - `spans` = every `ToolSpanLog` change in order (catch-up too) plus `{drop: id}` when the log prunes a span; TS mirrors them all and queues the non-drop ones for `drainSpans` only when `catchUp` is false (= TS `pendingSpans`).
  - `inbound` / `sent` = `PeerInbound` / `PeerSent` (always, `live: !catchUp`).
  - `more: true` → send the same `tracker.sync` again (only `nowMs` may change): it continues the pending run; pages add up to one TS `syncOnce`. A call whose args differ (`sessionId`, `cwd`, `epoch`, `catchUp`, `plan`) drops the pending run and starts a new one (lines already read stay read; the tailer keeps its target size).
  - `view` (last page only) = delta `{full?, main?, subs[]}`: `full: true` (first sync of a key, after a new epoch) = whole view, TS replaces; else only what changed since the last view (main when a main record gave signals, a subagent when it was discovered, gave signals, resolved or its msgIn / msgOut grew), TS merges by `agentId` (new ones appended = discovery order); nothing changed → no `view`. Fields: main state (`model`, `effort`, `currentTool`, `lastAt`, `tokens`, `contextTokens`, `peakContext`, `firstContext`, `cacheTtl`, `cacheAt`, `permissionMode`, `gitBranch`, `compactions`, `limitHit`, `lastReply`, `pendingAsk`, `codexCalls`, `deviceCallAt`, `portConflict`), per subagent in discovery order `{agentId, meta, startedAt, status, resolved, completedAt, msgIn?, msgOut?, state}`.
  - T3b: the delta is per field. Rust keeps the last sent main / sub maps; a non-full `main` carries only keys whose value changed, a removed key as `null`; a sub already sent carries `agentId` + changed top-level keys (`state` nested the same way, `null` = removed), a new sub comes whole; a dirty agent with no changed field is left out, nothing left → no `view`. TS `mergeView` patches field by field, so unchanged values keep their object identity.
  - Error `tracker` (unknown key), `args`, `plan`.
- `tracker.closeSpans {key, at}` → `{spans}` (= `closeOpenSpans`); `tracker.close {key}` → `{}`. Both may be sent without `id` (fire and forget); `tracker.open` / `sync` without `id` are ignored.
- One `ToolSpanLog` per tracker (main + every subagent), `ToolSpanLog::with_drops` records pruned ids.
- TS seam: `trackerSource.ts` `createTracker` (`CCM_CORE_TRANSCRIPT=rust` + `CCM_CORE_BIN` → `CoreTracker`, else `SessionTracker`), one shared `orrery-core transcript` child per collector (own process, separate from `CCM_CORE_USAGE`). Tracker requests never restart the shared core on timeout (`restartOnTimeout: false`, 30 s): a failed / timed-out / unknown-key reply → only that tracker reopens with a new key (old key closed) and a quiet catch-up; activity of pages read before the failed page is kept, later activity of that sync is lost; spans that are new or changed end / outcome after the catch-up (vs the mirror before it) are queued for `drainSpans`, so the store never keeps a stale open span. Reopen fails (core missing, more than 3 restarts a minute, timeouts) → that tracker switches to an internal TS `SessionTracker` (quiet catch-up, same span diff), logged once. Keys `t<n>` unique per collector process. `monitor.ts` `forget()` calls `tracker.dispose?.()` (`tracker.close` + unregister); `FinalizationRegistry` stays as a backup.
- T3b CPU (rust mode): `CoreTracker.takeChanged()` = view merged / record changed (shallow) / end moved since the last call; `monitor.ts` `syncTracker` publishes only then (most reconcile syncs read nothing new, and each publish rebuilt terminal + agents and diffed them). Node `SessionTracker` has no `takeChanged` → always publishes, as before. Safety net (deviation, rust mode only): `createTracker` gives `CoreTracker` `safetyNetMs` = `SAFETY_NET_MS` 4 s; a live `skipResolved` sync (the reconcile safety net, ~31 of 44 syncs/s in demo 30×6 because every registry write reconciles all 30 trackers) returns `[]` without a core round trip when a full or skip-resolved sync of that tracker finished < 4 s ago (file-scoped syncs from the watcher do not count and are never skipped; catch-up, full and file syncs always run). A missed watcher event therefore shows up at most ~4 s later than in Node mode; the 5 s reconcile interval always passes. The publish after it still runs when `takeChanged` says the record changed. Measured: one no-op skip-resolved sync costs ~380 µs in the core on Windows (stat / open ~20–25 µs, `read_dir` ~48 µs per subagent dir). Record parse (§2.2 too) goes through `prune.rs`: only the keys `extractSignals` reads are built into the `Value`, the rest is lexed without allocation (big tool results / thinking / `toolUseResult.file` never materialise); a deep or out-of-range value inside a skipped key no longer drops into the sanitize / Deep path (same signals). Tailer opens each file once per read. Not done: sharing one read between tracker and usage (`CCM_CORE_USAGE`): they run in separate `orrery-core transcript` children (usage on its worker thread with its own per-file offsets / debounce / cache v4), sharing needs one process and a hand-off of lines between the main thread and the usage worker — larger change, own WP if needed.
- Known differences: TS `toolSpans()` prunes the mirror at query time while Rust prunes at sync (a span pruned only on the TS side and seen again under the same id is re-added by TS, skipped by Rust); subagent `readdir` order is the OS order on both sides; meta JSON deeper than 128 levels or with numbers beyond f64 is `{}` in Rust; plan §2.2 list.
