# Nguyên tắc cốt lõi và các ngoại lệ chủ nhân đã duyệt

Chuyển nguyên văn từ CLAUDE.md (v110 P4). CLAUDE.md giữ 1 dòng tóm tắt mỗi ngoại lệ và trỏ về file này. Mọi ngoại lệ do chủ nhân duyệt; thêm ngoại lệ mới thì ghi vào đây trước.

Core principle: **Observe → Normalize → Broadcast → Render**. Monitoring must never send prompts to Claude Code, call the Claude API, or spawn another LLM agent, zero additional token cost. Single owner-approved exception (v51): the Workspace menu item **Compact…** submits one handoff prompt into an idle agent pane the owner picked, and (owner, 2026-11-06, Settings switch on by default) then submits `/compact` and the resume line by itself, stopping on manual typing, cancel or a 10-minute wait; with the switch off both are only typed / prefilled (docs §11x). Second exception (v81): `hand_back` from a DeepSeek pane submits one fixed hand-back prompt into the idle Claude / Codex pane that opened it (docs §11am). Third exception (v82): while `/bot-tele-receive` is on, a message from the owner's paired Telegram account that mentions the bot in a project topic is submitted straight away into that project's Claude / Codex Workspace pane, even while the agent is working (owner, 2026-11-20) (docs §11an). Fifth exception (owner, 2026-11-08): a tap on a `telegram_send` button that an agent pane attached types its value into that pane, submitted straight away, even while the agent is working (owner, 2026-11-20) (docs §11an). Fourth exception (owner, 2026-11-08): MCP `open_session` with `submit: true` from an agent pane submits its prompt in the new pane once the agent is ready, so jin-workflow can hand work to Codex when Claude hit its usage limit; links never submit (docs §11w). Sixth exception (v100, owner 2026-11-15): a click, double click, button bar press, queue chip or toast button on a Claude / Codex choice menu types the chosen key (number, Up / Down, Space, Enter) into that pane; every key follows a click by the owner, like a paste, and the app never answers a menu by itself (docs §11as); since v107 a tap on a menu bubble in the phone chat (`ws.menu`, after a 3 s undo) takes the same path (docs `remote-integration.md` §4.3); since v113 (owner, 2026-11-26) a tap on a choice button of a push notification takes the same path too: the tap opens the app (through the app lock when on) and only then sends `ws.menu` with the menu signature, never from the background, and a changed menu is refused as `stale`. Seventh exception (owner, 2026-11-12): since v97 the Flutter app Orrery Remote (`apps/mobile`, Android first) is a second frontend: after a paired, end-to-end encrypted (Noise) connection over LAN port 4320 or the Cloudflare relay (`apps/relay`) it receives session contents and terminal bytes and may open / close panes, type, edit files and run git / run commands; a prompt sent from the phone is submitted straight away, even while the agent is working (owner, 2026-11-20), and the phone can stop a working agent with Esc; env, secrets, app key and PTY tokens never leave the machine; remote control is off by default and dangerous actions confirm on the phone; since v113 the phone may also write text into the desktop clipboard and receive the desktop clipboard over the open encrypted session, each only on a tap, capped at 64 KB, blocked when it looks like a secret and never logged, and may upload photos only into `<project>/.orrery/inbox/` under names the desktop picks; a command that matches the desktop's danger rules needs device authentication on the phone first (docs §11au, `docs/orrery-remote.md`, `docs/remote-integration.md`, `.planning/PLAN-v97-mobile.md`). Env: `CCM_REMOTE_PORT` (4320). Eighth exception (owner, 2026-11-12, v98): push notifications to paired phones carry agent, session, project and the pending question / permission, the done time or the error, secret-masked, stripped of control / bidi characters and cut to 120 characters, shown on the lock screen; each phone has an "Include content" switch (on by default; off = the fixed text as before), the desktop can turn push off per phone (Settings → Remote bell), security alerts never carry an IP or a name; Web Push to the web app is end-to-end encrypted per RFC 8291 (VAPID key per machine in the keychain) and sent by the desktop straight to the push service; FCM to Android carries content only sealed to the phone's paired X25519 key and bound to the desktop's static key (ChaCha20-Poly1305; Google sees only the ciphertext plus the machine id and the kind) as a data message the app decrypts and shows itself, falling back to the fixed text when it cannot open it or the machine is not paired; old apps, "Include content" off and security alerts keep the fixed FCM text, and a phone gets the fixed notification plus the sealed probe until its background handler has proved it works within the last 48 hours (WP-56b, docs §7.7); since v113 (owner, 2026-11-26) a push for a pending choice menu may also carry up to 3 choice labels (each secret-masked and cut to 24 characters, inside the sealed part when sealing is on), the number of waiting panes and up to 2 masked pane labels (24 characters each) for the home screen widget and Quick Settings tile, a `running` / `done` / `open` / `clear` kind on their own lower quota so they never take the place of a question; since v113 an `apk` push, sent only when the owner taps "Send to phone" in the Run pane or turned on auto send for that project, carries the LAN download link with a one-time ticket, the size, the SHA-256, the app name and the variant, only inside the sealed part or the encrypted Web Push, never the file path (docs `docs/remote-integration.md` §7.6, `.planning/PLAN-v98-ios-pwa.md` #15–#20).
